## 零、为什么是这两件，而不是先做流速场 / 时间层

通读后按「证据硬度 × 对伤亡数字的影响 × 改动风险」排序：

| 候选 | 证据 | 对数字的影响 | 风险 | 排序 |
| --- | --- | --- | --- | --- |
| 相机 LOD 接进行为内核 | **代码里明写了**，三处 | 判断频率与避让同时受相机影响，所有数字都带相机偏置 | 小（删条件、去掉乘子） | 1 |
| 逐栋首层标高未接 JS | Python 侧已算出 21,213 栋、三组假设 | 室内一层进水判据错 3–4 倍 | 小（只换一个常量来源） | 2 |
| 流速场 | 无数据（`velocityMs: 0`） | 决定「冲走 / 倒塌 / 上屋顶」三类是否存在 | 大（要新数据源） | 后 |
| 时间层拆发布/收到/动身 | 只有 `p.warnAt` 一个时刻 | 改变动员节奏 | 中（要重排状态机） | 后 |
| 固定随邻居 / peersStay 越界 | 文献设计域 0–0.8，本项目≈1 | 避险人数 23–101 偏低 | 中（要重做邻居网络） | 后 |

前两项都是「先把明显的错接修掉」，不引入新数据、不改行为参数，符合「不为了结果好看改模型」。

## 一、相机解耦（表现层 LOD 不得进入行为内核）

### 证据（都在 web/src 里，行号以 2026-11-20 07:40 的状态为准）

1. **人-人避让只算相机看得见的人**
   `web/src/ped.js:1784-1791` 建 `buckets` 时 `if (!p.visible) continue;`，
   而 `p.visible = p.dist < VIS_DIST`（`web/src/ped.js:54`，`VIS_DIST = 360`）。
   `buckets` 的唯一用途是 `web/src/ped.js:2249` 的「前方有人」判断 →
   `p.latTarget = pedAhead ? 0.55 : 0`（`:2260`）。
   所以相机 360 m 外的行人互相「看不见」，永不侧让。
   同一段代码 `:1793-1804` 已经给**交通层**建了不裁剪的 `yb` 索引，注释还写着
   「交规用索引按真实存在的人建，不受相机距离裁剪影响」——
   同一份索引里，车看得见人，人看不见人。

2. **判断频率随相机远近变 2.2 倍**
   `web/src/live-agent.js:359`：
   `a.nextThink = a.t + a.kernel.think * (ctx.far ? 2.2 : 1);`
   `ctx.far` 来自 `web/src/ped.js:1877`（`p.visible === false`）。
   同种子同一个人，只因相机远近，决策间隔差 2.2 倍。

3. **关掉水面图层 = 全城失去水深**
   `web/src/main.js:2164`：
   `const pedFlood = (FLOOD && FLOOD.group.visible) ? FLOOD : null;`
   面板上点掉「水面」，一千人立刻在没有水的世界里行动。

默认机位 `web/src/main.js:153` `camera.position.set(1018, 24, -636)`（街面近景），
总览机位 `web/src/main.js:2748` 在 4 km 外。1000 人散布在核心区，
所以 headless 跑里绝大多数人的 `far` 为真。

### 改法（三处，都是「删掉表现层条件」）

| 文件 | 现在 | 改成 |
| --- | --- | --- |
| `web/src/ped.js:1784-1791` | `if (!p.visible) continue;` 建 buckets | 与人流索引同一口径（`p.enabled !== false && !p.inVehicle`），并把 `:2249` 改为查 `pedBuckets`（即 `yb`），删掉可见性裁剪的重复索引 |
| `web/src/live-agent.js:359` | `* (ctx.far ? 2.2 : 1)` | 去掉乘子，判断频率与人距离相机无关；`far` 只留给动画降频 |
| `web/src/main.js:2164` | 以 `FLOOD.group.visible` 为门 | 以「水帧是否就绪」为门（`FLOOD.frames > 0`），图层显隐只影响画不画 |

### 不做什么

- 不改 `VIS_DIST`、不改动画降频、不改任何行为参数。
- `skipRender` 的渲染跳过保持不变（那是渲染开关，不是行为开关）。

### 验收协议（先证伪，再改）

1. **改前**：`u_p20_s0` 跑 240 分钟，机位 A = 默认街面，机位 B = 总览（`__setView('city')`）。
   若两个机位的「判断总数 / 涉水暴露 / 避险 / 困死」有一项不同 → 相机耦合被证实。
2. **改后**：同样 A/B 再跑 240 分钟，两个机位除渲染相关的计数外应**逐格相同**。
3. 只有第 2 步通过，才算解耦完成；否则说明还有别的相机路径没找到，继续查。

## 二、逐栋首层标高接入 JS

### 现状

- Python 侧 `data/derived/building_foundation_fema.json` 已有 21,213 栋、三组假设
  （A_全国河岸 / B_老城排屋 / C_商业为主），取值只有 FEMA 四档：
  0.30（平板）/ 0.70（填土）/ 1.07（架空）/ 1.22（地下室）m。
- JS 侧 `web/src/kernel/floors.js:95` 仍是全城统一 `foundationHeightM: 0.457`（DC 旧规 1.5 ft），
  被 `floors.js:192`、`:244`、`:342` 无条件使用。
- 后果：同一场 50 mm/h 雨里「淹到一楼」的楼数，
  「轮廓任意点>5cm」163 栋 → 「统一 0.457」540 栋 → 「无首层高」3358 栋
  （`docs/首层标高校正_2026-11-18.md`）。

### 数据搬运（已完成，可回滚）

- 新增 `tools/export_web_foundation.py` → 输出 `web/assets/city/foundation_fema.json`（294 KB）。
  把 21k 栋 × 3 组压成「id 列表 + 每假设一条数字串」（取值只有 4 档，一栋一位数字）。
- 覆盖：前端 21,943 栋里命中 **21,147**，缺 **796** 栋 → 回退 0.457 m 并计数，
  不许静默当 0。

### 运行时接法

1. `web/src/kernel/floors.js`：
   - 新增模块级注册表 `setFoundationTable(json, scenario)` / `foundationMFor(b)`；
   - `assignFloor()` 用逐栋值（有 id 查表、无 id 用传入的 `foundation_m`），缺值回退 `SELF_SET.foundationHeightM`；
   - 返回对象加 `foundationM` 字段，供下游算「该层积多深」。
2. `web/src/terrain.js:346` 的 `loadBuildings()` 之后加载 sidecar 并注册；
   默认假设 `A_全国河岸`，允许 `?foundation=B_老城排屋` 切换做敏感性。
3. `web/src/crowd-life.js:376` 的 `assignFloor({...})` 传 `id: best.id`；
   `:603` 的 `q` 加 `foundationM`。
4. `web/src/ped.js:1974` 的 `INC.tick` 上下文加 `foundationM`；
   `web/src/incidents.js:367` 现在写死 `floorElevationM(r.effFloor, undefined, ...)`
   （即永远用 0.457），改为读 `ctx.foundationM`。

### 验收协议

- 先只跑 `u_p40_s0` 240 分钟，检查：①缺值计数 = 796；②有逐栋值的楼，一层地板高程与
  `foundation_fema.json` 逐栋一致（抽 20 栋手算）；③`final.sim.incidents` 三套死因合计仍相等。
- 敏感性：A / B / C 三组各跑 240 分钟，看室内一层死亡与「避险成功」怎么变；
  报数必须写清是哪一组，禁止只报最有利的一组。
