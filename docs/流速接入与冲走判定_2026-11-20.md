# 流速接进伤亡判定 · 与时间层动身门控（2026-11-20）

这一轮做了两件模型侧的事：**把流速从「有数据但没人用」变成「真的进判据」**，以及**给时间层加了一道动身门控**。过程中查出两个会让结论静默失效的 bug，一并记在这里。

## 一、为什么之前「有流速也没用」

`tools/flood/build_velocity.py` 已经把八工况的 `vel`/`dir` 导出到 `web/assets/flood/<case>/`（见 `docs/流速场导出_2026-11-20.md`），但浏览器侧有三道坎，前两道是 bug：

### Bug 1 · 采样永远读第 0 帧（整条冲走判据静默失效）

`web/src/flood.js` 的 `depthInfo()` 调 `sampleFlow(x, z, undefined, _fl)` 想要"当前帧"，而 `sampleFlow` 把 `t` 原样喂给 `bracket(t)`：

```js
const tt = Number(t);          // Number(undefined) === NaN
if (!Number.isFinite(tt)) return { i0: 0, i1: 0, f: 0 };   // 开局全干帧
```

于是对每一个人的每一次采样都落在 t=0 的全干帧上，**恒等于 0 m/s**。这不是"流速太慢"，是"根本没读"。

修法：入口把 `undefined`/`null`/非数统一换成 `curMinute()`，注释写死"不能把 undefined 直接喂 bracket"。

### Bug 2 · 室内被套上室外流速

第一跑判出 5 例「地下室·被水流冲走」——地下室的水是顺着门缝和楼梯渗进来的，没有水流。原因是室外采样到的流速被直接套到地下室里，而地下室当地水深还是"室外 + 2.2 m 埋深"。这属于采样错位，不是物理。

修法：`incidents.js` 里 `vFlow = (indoor || inBasement) ? 0 : …`，室内回到静水判据。

### 坎 3 · 流速帧要预热

`frameBytes()` 只取水深帧。决策层第一次问流速时缓存还是空的，拿到的就是 0——等于把急流当静水，判据又一次静默失效。现在水深帧入库时同时 `wantKind(f,'vel'); wantKind(f,'dir')`，让流速跟水深一起进缓存。

**验证**（`web/devtools/probes/probe-speed.mjs`，u_p80_s0 @1125 分，747×640 栅格 12 格撒点）：

| 指标 | 值 |
|---|---|
| 湿格（≥5 cm） | 367 |
| 其中有流速 | 293 |
| 深格（≥1 m） | 30 |
| 其中有流速 | 22 |
| 湿格平均流速 | 1.455 m/s |
| 最大流速 | 3.0 m/s（量程顶） |
| 深格平均 HR | 3.53 |
| 最大 HR | 7.03 |

样本如 `d 1.66 / sp 2.21 / hr 5.50`、`d 2.09 / sp 0.33 / hr 2.73`。探针第一版之所以打印"湿格流速全为 0"，是因为它在同步循环里连采 3300 点，而 vel/dir 帧是异步 fetch——探针自己的错，不是运行时的错。

## 二、冲走判定为什么改了两次

判据链条：`HR = d(v+0.5)+DF`（FD2321）→ `isUnstable`（ARR 的 D·V 与限值静水深）→ `sweptRiskPerSecond(HR)` 累积 → 超过 `personalThreshold(i)` 判死，死因单列 `路面·被水流冲走`。

| 版本 | 锚点（HR=2.5） | 附加前提 | u_p120 全天冲走死亡 |
|---|---|---|---|
| 第一版 | 0.0115/s（50% 在 60 s） | 无 | **54**（总死 59） |
| 第二版 | 0.004/s（50% 在 2.9 分钟） | 步速 ≤0.35 m/s | **29**（总死 38） |
| 第三版（v4） | 同上 | 再加**流速 ≥0.5 m/s** | 待 v4 结果 |

第一版显然错在把 FD2321 的「危险度分级」直接读成「必死」；第二版降了锚点，但 29 例里多数其实是**站在 1.4–1.8 m 静水里走不动**——那是困死，本来就有更合适的判据（深水耐受 → `路面·被困`），两条都开等于同一件事记两次账。

第三版加的门是：`SWEPT_MIN_FLOW_MPS = 0.5`。理由写在 `web/src/kernel/flow-hazard.js` 的注释里——HR 公式里那个 `0.5` 是 FD2321 给静水补的**拟流速**，意思是"水够深就已经危险"，不是"静水能冲走人"；要真的被水带走，需要有把还站着的人整体推移的水流，0.5 m/s 是这个事件的**可辩护下限**（ARR/FRMRC 的涉水稳定性参考流速：0.4 儿童 / 0.8 受训成人 / >1.2 极端）。

**这一条是【目前自己定的】**，不是实测值。台账已记，交付前要做 0.3 / 0.5 / 0.8 m/s 的敏感性。

## 三、时间层动身门控

`docs/时间层设计_2026-11-20.md` 把预警拆成发布/收到/动身三个时刻之后，动身时刻本来只用于报告、不参与决策，等于白拆。现在接上了：

`web/src/ped.js` 里"下雨了先躲一下要不要立刻跑"那个分支改成先问一句：

```js
const waitingToDepart = timeLayerOn() && Number.isFinite(p.departAt) && NOW_MIN() < p.departAt;
```

- 为真：`p.tryT = 0.5`，首次记一条 `wait`（"雨已经下大了，但还在收拾东西，没动身"），并设 `p.prepping = NOW_MIN()` 供 `fleeStats()` 统计。
- 为假：走原来的 `startFlee(p, 'rain')`。

**水已经没过涉水线那条分支不受门控**——那时候是逃命，不是准备。这一条是刻意的：门控只能推迟"因为下雨就想跑"的决定，不能推迟"水已经到脚踝"的逃命。

`fleeStats()` 新增 `prepping` 计数（当前仍在准备、还没动身的人数）。

## 五、遗留

1. **v4 还没出结果**。危险人·秒从 3682 涨到 13008 是预期的——门变严之后，还没到"被冲走"程度的人会继续待在危险水里累计暴露，这个量不该随着死亡数一起降。
2. **仍然判不了建筑倒塌与溃决区**（台账 §4.2 已改）。被冲走这一类补上了，倒塌这一类还是空的。
3. **风险曲线、0.5 m/s 下限、0.35 m/s 步速前提全是自设**，三项都得做敏感性。
4. `hazard-input.js` 里那条"流速取 0"的旧近似还在，只服务没带流速的老工况，不要和新路径混用。
