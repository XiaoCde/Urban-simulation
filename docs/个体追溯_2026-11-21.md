# 个体行为追溯（2026-11-21）

导师点评里最硬的一条：**必须支持个体行为追溯——定位某个受困/溺亡者，复现其完整过程，而不是只能看随机个体。**
这一节记的就是这件事：怎么打开、看到什么、以及它当场揪出的三个 bug。

## 一、怎么用

```bash
# 1) 起静态服务（sim-day 不自起服务）
cd web && node serve.js 8140

# 2) 追一个人跑一轮：SIM_TRACE=<人序号>
SIM_TL=1 SIM_TRACE=74 node web/sim/sim-day.mjs 240 24 240 web/out/_trace/u_p80_s0_p74.json 1020 u_p80_s0 20261117

# 3) 把 trace 渲染成可读时间线
node tools/trace/timeline.mjs web/out/_trace/u_p80_s0_p74.trace.json web/out/_trace/u_p80_s0_p74.json
```

页面上也可以直接看：地址加 `?trace=<人序号>`，控制台 `window.__trace()` 返回同一个对象。

## 二、记录了什么

四类，按同一根时间轴对齐（分钟数）：

| 类型 | 谁写 | 内容 |
| --- | --- | --- |
| `identity` | `web/src/ped.js` | ACS 逐人属性：年龄、性别、SOC 大类、经验、有无车、工作场所 |
| `tick` | `web/src/ped.js` | 逐分钟：坐标、所在（home/work/road/shelter）、室内与否、脚下水深、雨强、是否在车里 |
| `judge` | `web/src/cohort.js` | 每次判断：五道门各读到什么（收到/危险度分级/动员率/选择概率/阻碍）、乘出的概率、最后落到哪个动作、为什么 |
| 事件 | `web/src/incidents.js` | 状态跃迁：下地下室、涉水、被困、受伤、熄火、弃车、避险、死亡 |

写入是**只对被追的那一个人**（`traceWanted(i)` 一次比较就返回），别人零开销。

## 三、当场揪出的三个 bug（都属于"结果恒 0 还不报错"这一类）

1. **`kernel` 对象上没有 `i`**。`makeKernel(i, …)` 返回的 `k` 里有 `id: '状态/年龄带'` 这种标签，却没有喂进去的那个 `i`。于是 `traceWanted(k.i)` 恒假 —— judge 一条都记不下来，界面看着正常、文件里没有判断记录。已在 `web/src/cohort.js` 的 `k` 上补 `i`。
2. **逐分钟去重用了小数分钟**。`NOW_MIN()` 返回的是小数（帧间隔 1/60 分），直接比较等于每帧都"不同"：一次 4 小时、240 人的短跑就写满 40000 条上限、**后面的死亡事件根本挤不进去**（第一次跑 `truncated: true`，事件链是空的）。改成按 `Math.floor(t)` 去重后，同一跑 242 条，`truncated: false`。
3. **死亡之后还在写事件**。案例 74 号：19:50:28 判「车内溺亡」，19:51:35 又记一条「弃车改步行」。原因是 `incidents.mark()` 不查状态就 `push`，车/交通层拿着已经死了的人继续抛事件。已在 `mark()` 开头加死亡短路。
4. （附带）**开车的人没有 tick**。走路的人在步行分支写轨迹，开车的人走另一条分支 `continue` 掉了 —— 于是「死在车里」这个案例的 trace 只看到「他在家」和「他死了」，最关键的五分钟是空的。已在驾车分支补 `traceTick`。

## 四、追出来的例子（案例 74 号，u_p80_s0，240 人，1020→1260 分）

身份：35 岁女性，SOC 21（社区服务），经验 0.80，ACS 记录里**户车数 0**，行为原型「高地住宅 · 有幼儿 · 自驾 · 预警及时」。

| 时刻 | 事件 |
| --- | --- |
| 18:08:06 | 下到地下室抢救财物 / 查看水泵（水深 0.05 m） |
| 19:45:01 | 去 708 m 外购物／取退货，家里有车且路可通行，开车 |
| 19:45:19 | 前方 1 名行人，减速让行（水深 0.10 m） |
| 19:45:20 | **16 cm 积水，发动机进水熄火** |
| 19:46:00 | 车停在路上，水深 0.15 m |
| 19:49:29 | 脚下 36 cm，进入涉水状态 |
| 19:50:00 | 水深 0.58 m |
| 19:50:28 | **车内溺亡（0.78 m）** |

这条链子自己说明了三件事，也说明现在的模型哪里还不对：

- **她本来不该有车**。ACS 记的是户车数 0，`hasCar` 也是 false，可 `tripStart` 的理由写着「家里有车且路可通行」。场景层的车池与 ACS 户车数还没打通——这正是「仿真分布要和真实数据集一致」这条要求没做到的地方。
- **她决定开车的那一刻，水只有 0.10 m**。按车辆稳定性（Smith et al. 2017：0.15 m 开始被推移、0.60 m 漂浮），这个决定在当时不算离谱；问题在于**没有"前方 700 m 路线的水情"这个输入**，她只能看脚下。
- **17 分钟后才弃车**（而且这次因为修了顺序 bug 被正确抑制掉了）。真实情形里 0.6 m 漂浮之前人就该出来；现在弃车时机由车/交通层自己定，与 `incidents` 的困死判定是两套，需要合成一处。

## 五、限制（必须跟着结果一起说）

- 只追一个人：这是刻意设计（全量 trace 会把一轮仿真的内存翻几倍），要看三个人就开三个进程各追一个。
- `judge` 是抽稀过的（结论变了或满 5 分钟才留一条），不是每一条判断；要全量把 `web/src/trace.js` 的 `traceJudge` 去重去掉即可。
- 时间线里的「判断」行只在**走路**的人身上密集出现；长时间在家、没有激活目标的人一天可能只有零星几条 —— 这不是丢失，是那时确实没有决策。
- trace 文件不参与结果统计；它是证据，不是指标。

## 六、下一步（按导师那几条排）

1. 车池 ↔ ACS 户车数打通（案例 74 就是一个现成的反例）。
2. 路线级水情输入（现在只有脚下 + 前方 4/9 m 两个采样点），否则「该不该开车出门」永远判不准。
3. 把「个体视角渲染」接上：现在是离线跑完再回放，`?trace` 已经能定位到人，缺的是镜头跟人。
4. 批量版本：`SIM_TRACE=all-dead` 之类，跑完自动把每个死者各导一份时间线，用于人工抽查死因分布是否整体可信。
