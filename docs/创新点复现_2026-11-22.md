# 四条创新点：一条命令复现一个证据（2026-11-22）

> 用途：论文附录 / 答辩现场 / 换机器重跑。每条都给出**命令 → 产出 → 该怎么读**，
> 不写「跑一下就知道」。所有命令都从仓库根执行，先 `cd web` 再跑仿真类。
>
> 前置：`node serve.js 8140` 必须在跑（`sim-day.mjs` 用浏览器加载页面算，
> 没有静态服务的报错是 `net::ERR_CONNECTION_REFUSED`，不是模型错）。
> 20 核机器上并发 **2** 是实测的稳定点：再多会让「同族墙钟参照」失真。

## ① 门结构 vs 单式效用（消融）

```bash
cd web
# 4 工况 × 2 结构 × 1000 人 × 全天 1440 分，同 seed 20261117
SIM_CASES_MAX=999 bash sim/run_ablate_v1.sh 2 1000 1440 out/ablate_v1
# 生成论文表（先核对「对照条件一致」，不一致的行拒绝比较）
node tools/check/paper-tables.mjs ablate out/ablate_v1
```

- **产出**：`out/ablate_v1/gate__<工况>.json` / `single__<工况>.json`；
  `docs/消融_数据_2026-11-22.md`（表）。
- **怎么读**：先看表的第三节「对照条件自检」——people/seed/startMinute 必须逐工况一致。
  然后只看两件事：① 死因结构（`deathsByCause`）有没有变；② 逐小时累计撤离曲线
  （`node tools/check/decide-ab.mjs a.json b.json --hourly`）。
  **不要拿死亡总数当卖点**——它由水情与人口决定，两种结构都可能给出 8 或 9。
- **快速版**（15 分钟出方向，不是结论）：300 人 / 300 分 / 起点 1020 / `u_p120_s0`，
  见 `docs/消融_门结构vs单式_2026-11-22.md` 的第二节。

## ② 可审计建模（常数登记 + 机检 + 绊线）

```bash
cd web
node tests/check-param-evidence.mjs          # 648/648
node tools/check/param-table.mjs > ../docs/参数依据表_V7_2026-11-21.md   # 表由代码生成
bash tools/check/inject-demo.sh              # 证明「机检真的会红」
node tests/check-tripwires.mjs               # 69/69（四条绊线）
```

- **产出**：61 条常数、648 项断言、64 行表、注入演示的两条红。
- **怎么读**：`inject-demo.sh` 会故意干两件坏事（改一个数字、加一条没理由的自设常数），
  看检查器是否**当场打红**，然后自动还原。这是「不是靠自觉，是靠机制」的唯一证据。
- **抓错案例**（论文里比数字更值钱）：`docs/可审计建模_2026-11-22.md` 的三张表——
  RELP 关系码写错导致照护门命中 0 人；peersRide 恒 0 且 peersStay 方向反；
  `bindCrews` 给无车户发车。

## ③ 个体级伤亡归因

```bash
cd web
node tools/check/trace-deep.mjs out/ablate_v1 --out=../docs/个体归因_数据_2026-11-22.md
node tools/check/trace-deep.mjs out/surge_v1  --out=../docs/个体归因_数据_跨驱动_2026-11-22.md
```

- **产出**：第 0 节「完整性核对」（个案数必须等于汇总 dead，否则标 ❌ 截断）、
  死因构成、浸泡时长分布、死亡窗口三分法、年龄组 × 人口倍率。
- **怎么读**：先看第 0 节。任何一文不值的结果都可能来自截断——
  我们上一版 141 个死者只导出了 62 个（`exportCases(12)` 只导最深的 12 个）。
- **单个死者全流程复现**：`SIM_TRACE=<i>` 环境变量 + `web/src/trace.js`，
  或 `node tools/trace/cases.mjs <结果.json>` 批量出每人一份 md。

## ④ 跨驱动（降雨型快涨 vs 河道慢涨）

```bash
# 1) 先生成水情（python，不经过浏览器；res 8、一天 24 h，一套约 5–7 分钟）
python tools/flood/build_surge_only.py         # u_p0_s2.71 / u_p0_s4 / u_p0_s6
# 2) 再跑人（1000 人 × 全天，一套约 60–70 分钟）
bash web/sim/run_surge_v1.sh 1000 1440 out/surge_v1
# 3) 并排（降雨侧拿 u_p24_s0 gate 当对照）
cd web && node tools/check/paper-tables.mjs driver out/surge_v1 out/ablate_v1 --rain=u_p24_s0
```

- **产出**：`docs/跨驱动_数据_2026-11-22.md`（表）。
- **怎么读**：慢涨工况若「车内」死亡下降、「地下室/低洼地面」上升、首次撤离推迟，
  说明决策层在读输入；若两者死因结构几乎一样，说明决策层对涨水速率不敏感——
  那是个该记录的负结果，不要藏。
- **必须先知道的一件事**：河道增水在本求解器里**原本淹不进街道**（numba 通量门
  `hfm < h_min` 会门掉「河格 h=0 → 干陆格」的方向）。所以 4.0 / 6.0 m 两套必须带
  `--river-overtop-cw 1.7`（显式堰流源项）；不带的话三档全是 0 ha。
  证据与三个实现坑见 `docs/跨驱动_2026-11-22.md`。
