# 模型核心问题与优先级（2026-11-20，独立诊断）

> 这份文件是我通读全项目后自己的判断，不是上一位 AI 结论的复述。
> 每条都写了证据位置；「性质」一栏区分：**缺陷**（代码与设计意图矛盾）/ **假设**（无依据但已标注）/ **缺失**（整块能力没有）。

---

## 0. 先纠正一条流传的结论：p20 不是模型卡住

上一位 AI 的记录是「p20 卡住，两次跑到 440/840 分钟无声停止」。本次实测：

| 证据 | 数值 |
|---|---|
| p20 与 p40 在 40–840 分的「判断(事件)」计数 | **逐行完全相同**（10 / 1150 / 13381 / 37584 / 76472 / 120136 / 158745 / 185085 / 213711 / 223245 / 226513 / 229775 / 297336 / 494449 / 813560） |
| 强制 GC 后的存活堆（40/80/120/160 分） | **525 MB，四点恒定**（不是泄漏） |
| DOM 节点、纹理、几何、场景子节点 | 548 / 70 / 201 / 8，四点恒定 |
| 单批（100 帧 = 4 分）墙钟 | 3.7–4.4 s，无退化 |

结论：**内核没有卡死，也没有内存泄漏**。之前那次「无声消失」是进程/页面被杀（宿主内存压力或渲染进程被 OOM），
日志里既没有异常也没有收尾，符合被 SIGKILL 的特征。
`web/sim/sim-day.mjs` 现在已加：逐帧墙钟 + 每 50 帧 PROG 心跳 + 每批硬超时，
真卡死会打印「第几分钟 / 第几批 / 当时在场多少人」并落 `.stuck.json`，不再无声消失。

**这条很重要**：p20 与 p40 在 840 分前是同一条轨迹，说明「420–840 分没有降雨」这件事上
两个工况本来就该一样；把 p20 的差异归因到水动力是错的。

## 1. 缺陷：表现层 LOD 被接进了行为内核（相机决定模型结果）

这是本次通读最实质的发现。三处：

### 1.1 人会「看」不到被相机裁掉的人
`web/src/ped.js:1784-1791` 建人-人空间哈希时 `if (!p.visible) continue;`，
`p.visible = p.dist < VIS_DIST`（`web/src/ped.js:54` VIS_DIST=360，`:1626`）。
这个 `buckets` 唯一的用途是 `web/src/ped.js:2249` 的「前方有人」判断，
于是**相机 360 m 外的行人互相看不见**：即使两人擦身也不会侧让（`p.latTarget` 恒 0）。
`web/src/ped.js:2167` 的注释自己写着「城市总览机位下 3000 人全在 VIS_DIST 之外」。

### 1.2 被裁掉的人「想得更慢」
`web/src/live-agent.js:359`：
```js
a.nextThink = a.t + a.kernel.think * (ctx.far ? 2.2 : 1);
```
`ctx.far` 来自 `web/src/ped.js:1877` 的 `p.visible === false`。
所以**同一个人、同一个种子，只因相机远近不同，判断频率差 2.2 倍**。
验收跑的正是城市总览机位 → 全城所有人都在走这条 ×2.2 分支。

### 1.3 水层显示开关会关掉整个水-人耦合
`web/src/main.js:2164`：
```js
const pedFlood = (FLOOD && FLOOD.group.visible) ? FLOOD : null;
```
交互面板里关掉「水面」这一层（`web/src/main.js:1040` `onWater`），
`PED.update(h, camera, null)` 就会拿到 null —— 一千人瞬间失去水深，
避难、涉水减速、溺亡全部消失，而时钟照走、没有任何警告。

**性质**：缺陷（不是设计选择）。三处都是「为了省 CPU/为了显示」写的，
但省下的对象落在了**行为**上，不是**渲染**上。
**修法**：`buckets` 按 `p.enabled !== false && !p.inVehicle` 建（和交通层 `yb` 一致，那里已经修过同一个 bug，
见 `web/src/ped.js:1793-1804` 的注释）；`far` 只用于动画/阴影降频，不再改判断间隔；
`pedFlood` 与水层显示解耦。
**后果**：8 工况全部数字会变，必须整族重跑 —— 这不是调参，是去掉一个非物理输入。

## 2. 缺失：首层标高没进 JavaScript（唯一的致死通道因此偏了）

- Python 侧已校正（`data/derived/building_foundation_fema.json`，FEMA 分位数映射，三组假设 0.30–1.22 m）。
- JS 侧仍是**全城统一 0.457 m**：`web/src/kernel/floors.js:95`，被 `:192/:244/:342` 无条件使用。
- 现在的死亡几乎只剩「下地下室」一条（见 §4），而它判「地下室进水」用的是室外积水 ≥ 0.05 m（`web/src/kernel/floors.js:120`），
  与建筑台基高无关；**室内一层进水**才吃台基高 —— 于是台基高错 0.457 vs 0.30/1.07，
  恰好把「室内一层被淹」这条通道整块推错 3–4 倍（文档 `docs/首层标高校正_2026-11-18.md` 已算过淹楼数 163 vs 540）。

**性质**：缺失（数据有、代码没接）。
**修法**：把逐栋 `foundation_m` 并进 `web/assets/city/buildings.json`（新导出脚本），
`assignFloor` 读楼自己的值，缺值时退回 0.457 并在报告里记「无台基高的楼层数」。

## 3. 缺失：没有流速场，于是没有「被冲走」这一类死亡

`web/src/kernel/floors.js:271-273` 自己写明：没有流速场，LifeSim 的
「水深×流速倒塌」「上屋顶」「冲走」三类都不实现。
DC 的城市内涝以地下室溺亡为主（Thieken 2026 的 224 例里 131 例室内、其中 29 例地下室），
所以缺流速对**当前**城区暴雨工况影响有限 —— 但一旦做山洪/河道溃决工况，这条就成了主漏。
**性质**：缺失，优先级低于 §1/§2。

## 4. 假设越界：同伴留存项超出文献设计域，导致「避险」几乎不动

- `web/src/kernel/choice-model.js` 用 Borowski 2023 的 peer 系数，但
  Table 3 的自变量设计范围是 **peer staying 0–0.8**（均值 .19、SD .22）；
  项目里实际邻居留存率接近 1，**超出设计域**，只能算外推。
- 结果：p40 全天 1000 人「避险」只有 **23 人**，困死 1 人。
  这不是「模型保守」，是**一个变量被顶在饱和区**，模型对它不敏感了。
- 另外原文 cost 项在偏好空间是 lognormal（保证负号），项目用三项独立正态 + 自设 .50/.80 缩放
  （`web/src/kernel/choice-model.js:189` `knowledgeToActionScale`、`:304-307`）。

**性质**：假设，且已越界。**不要为了「避险率好看」去硬调系数** —— 正确做法是把它作为敏感性维度，
并在报告里明说「本工况的同伴项处于文献外推区」。

## 5. 缺失：时间层没有拆成「发布 / 收到 / 动身」

现在只有一个 `p.warnAt`（`web/src/ped.js:1884-1895`，见水 − 前置时间），
Kreibich 2017 的领先时间（中位 8–96 h，随雨型差异极大）和 Silva 的动员曲线
（`web/src/kernel/mobilisation.js` 只做 8/24/72 h 三时点插值）都无法作为**可调情景**。
政策上最有用的一档（提前 1 h 预警 vs 提前 6 h）现在跑不了。
**性质**：缺失。优先级：中高（这是「突发事件仿真」真正的政策接口）。

---

## 6. 结果层：死亡数 1 人，工况排序没有统计意义

p40 全天：判断 2223 万次、事件 596 万条，**死 1 人**（地下室进水）。
p20/p80/p120 也都在同一量级。于是：
- 八工况的「死亡」列本质是 0/1 的伯努利抽样，**跨工况排序是噪声**；
- 三套死因口径（cause/zone/legacy）合计相等这条校验，在 1 人的样本上**恒成立**，
  证明力极弱（我已经在 p40 上验过：三套都是 `{地下室…:1}`，合计 1 = dead）。
**性质**：方法论缺陷。**修法（不改物理）**：报数从「死几人」改为
①「累计被困人·分钟」②「累计受伤」③「避险人数」④按逐人风险概率积分的**期望死亡数**（可给出区间），
并在 `.md` 里同时给点估计与期望值。这样八工况才可比。

## 7. 工程：没有纯 Node 内核入口，单工况 24 分钟 → 敏感性分析做不了

现在每次模型改动要 8 × 24 分钟 ≈ 3.2 小时（并行 3 时约 1.6 小时）。
`web/src/kernel/*` 已经是纯数值层（无 window/document/three），但**人的主循环在 `web/src/ped.js`**，
那里和 three 的 `Vector3`/`Object3D` 绑死。真正的 Node 入口要先做一层「位置/朝向的最小载体」抽象，
风险高、收益是把单工况压到分钟级。
**性质**：工程债。优先级：在 §1/§2 修完之后（否则内核还在变，白搬）。

## 8. 我自己排的优先级（与上一位 AI 的顺序不同）

1. **p20 跑完 + 三项校验**（已在跑，见 §0；判断数逐格一致、三条死因合计相等）。
2. **§1 相机解耦**（缺陷，改动小、证据硬）→ 单跑 p40 对比，量化 LOD 的影响。
3. **§2 首层标高接进 JS** → 再跑 p40 对比。
4. 上面两项一起定稿后，**八工况整族重跑一次**（分族报告，禁跨族横比）。
5. **§6 报数口径改造**（期望死亡数 + 被困人·分钟），让八工况可比。
6. **§5 时间层拆分**（发布/收到/动身三档可调）→ 做预警提前量情景。
7. **§3 流速场**（需要 2D 水动力输出流速，Python 侧先补）。
8. **§7 Node 内核入口**（内核稳定后再搬）。
