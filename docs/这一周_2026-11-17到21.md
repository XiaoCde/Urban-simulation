## 11-17：修 bug，先立基线

这轮做四件事：查没修的 bug 和边界、评结构、找文献出处、汇总风险。硬约束是"不破坏现有功能"，所以顺序是：先采 28 组正常输入的输出存成 `web/out/kernel_baseline_before.json`，改完再采一次，逐字段差异 0；再把本轮改动用 git 暂时收起，改前改后各跑一次同参数短仿真（u_p16_s0、120 分钟、240 人、种子 20261117、2 并发），逐字段差异也是 0。

修掉的问题里，有几条真会算出错数：

- `kernel/hazard-input.js` 查表键印的是 `'0.60'`、`'0.90'`，代码用 `String(0.60)` 得到 `'0.6'`、`'0.9'`，取到 undefined，水深一过 0.35 m 涉水步速就恒为 NaN
- `kernel/mobilisation.js` 动员点表相邻时刻相同会除零，空表直接抛错，插值结果还会越出 [0,1]
- 情景分档越界产生 NaN 概率，`clamp` 不拦 NaN，整条决策链被污染
- `src/flood.js` 的 `fetch` 没查 `r.ok`，水深帧 404 的错误页被当数据缓存
- `src/incidents.js` 死因字符串里嵌了水深、判据、概率、分区，每个死者字符串都不同，`deathsByCause` 按字符串计数等于没统计
- `src/ped.js` 日末段下地下室的人一整天出不来（`basementUntil` 超过 1440，比较恒真）

边界类还有二十来条，正常输入下逐位不变。验完是 13 个纯 Node 自检全绿，浏览器回放 8/8，楼层运行时 4/4，`node --check` 语法错误 0。

同一天还出了文献核查补录、问询清单、检索方向、降雨工况结果。

## 11-18：体检，加上首层标高第一次接入

白天固定种子重跑 8 个工况（并发 4），同时做只读体检。体检三层：内核边界、代码正确性、文档与数据出处、工程结构。结论是内核边界守住了（`web/src/kernel/` 下没有真的 window/document/three，命中全在注释里），没查出严重问题，但列出几条隐患：24 个浏览器验收脚本只有 1 个固定了种子；预警有两套初值并存；同一组实测阈值在 `params.js` 和 `thresholds.js` 各存一份。

当场修了两条跟数字无关的：文档里写的复现命令是过期脚本名；`district.html`、`office.html` 已经归档到 `web/_legacy/`，但启动脚本和 README 还指向根目录。

首层标高这块第一次接进来。原来的判据是"建筑轮廓框内任意一点水深超过 5 cm，整栋算淹"，楼角有一洼水就报淹，淹楼数系统性偏高。改成"水要淹过这栋楼的一楼地面才算进水"，补的是逐栋基础高度。

数据先查本地：DC 官方 3D 建筑数据 `data/dcgis/buildings_3d.json`（22,697 栋，每栋带 `MIN_Z`），用 `tools/match_building_foundation.py` 按质心落框匹配，21,213 / 21,899 = 96.9% 对上。美国陆军工程兵的 NSI 2022 有逐栋 `found_ht`，但本机经代理访问返回 502，拿不到。最后用 `MIN_Z` 当基础高度，并且**把台基截断在 1.2 m**，这一场雨报淹 659 栋（按本文算法 540 栋）。

当晚自查 FEMA 规范发现这个 1.2 m 截断没有依据，而且把台基高估了 3–4 倍。改用 FEMA 默认台基高度做分位数映射校正后，同一场雨的淹楼数从 659 降到 130–200 栋。这条修正是整周唯一一次"自己定的工程处理被自己的核查推翻"。

## 11-19：文献 4，加上六处决策改动

上午接文献 4。第一个结论是否定自己：D-1（Li, Chen, …, Song 2025，*Chaos, Solitons and Fractals*）和我们 `params.js:122` 涉水步速表的出处（Li et al. 2026, *J Hydrol* 672:135395）是同一批中科大泳池实验的两次发表，水深档、速度、参与者都对得上，所以**不能当独立验证**，也不能用它替换现有步速表。它有用的部分是密度×速度、跟随行为，将来给步行层加"拥挤时减速"才用。

C 组死亡情境数据接进了报告层，非溺亡比例要往下调。A 组从众抽完后发现更麻烦的事：我们的从众输入是两极的（要么几个人都在留，要么都在走），文献里是连续的比例分布。

下午六步执行记录，六处决策逻辑改动，都是为了让人的反应更像真的：

3. 威胁交互 −9.27 / −21.13（p=0.000）的后果看清了：威胁一上来，同伴留下那 +7.76 会被抵成负数
4. 雨强跨档立即重估，30 分钟窗口降为兜底
5. 修了"深水走得和干地一样快"：`wadingSpeed` 此前只喂决策输入，位移完全不受水深影响，改成 `web/src/ped.js:2376-2385` 的 `spd *= Math.max(0.25, Math.min(1, vd/v0))`
6. 死因从四类笼统说法改成"地点×动作"两维，能和意大利 514 例、澳大利亚 1,859 例、德国 224 例个案逐条对照

## 11-21：核系数落点，发现两处接错

上午先定位停点，靠 `web/out/` 文件时间戳排的，结论是停在 v4 第四档刚开头。

接着把论文系数一个个对着变量核了一遍，每个都能追到具体行（落点表在 `docs/决策模型口径核查_2026-11-21.md`），没有编出来的数。但有两处接错：

一处是尺度。论文系数是每美元、每分钟、每英里的边际效用，代码先把四个量压到 0–1 再乘。按 Table 3 印的范围换算，成本压 40 倍、旅行时间和等待时间各压 60 倍、步行距离反放大 2 倍。结果是"绕路太贵所以不撤"这条机制基本不响。

一处是空转。`web/src/cohort.js:165` 读 `warningInformation`，全项目没有一处给它赋值，认知层的 0.147 一直乘 0。

改了三处，都不动默认行为：`web/src/kernel/attributes.js` 加 `FEED_MODE` 开关（默认还是老口径）、`ATTRIBUTE_META.selfSet` 登记压缩倍数、`cohort.js:165` 加注登记为未接入。

没直接改的原因写在核查文档里：成本系数 −3.71 的单位没核实。按每美元算，11.60 美元 × −3.71 = −43，会把 ASC 4.22 压死、给出接近 0% 的撤离率；按每 10 美元算，−4.30 正好和 4.22 平衡。后者更可能是对的，但这是推测。原文 PDF 抓下来是空的，读不到 Table 3/4。
