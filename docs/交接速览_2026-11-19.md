## 〇、三十秒

用华盛顿特区的真实测绘数据在 Three.js 里重建城市，跑 1000 个带真实人口属性的个体，看暴雨内涝时人怎么决策、怎么伤亡。

**当前状态：代码改到第六轮（六步改动全部落地），8 个降雨工况重跑到一半。** 前四个「全天雨」已有完整结果，后四个「傍晚暴雨」2026-11-19 晚上重跑中。

**最要紧的一句话**：这个模型现在**能证明自洽，不能证明对得上现实**——外部验证做了两次，两次都是阴性（见 §6.4）。

## 五、文献分类：101 篇怎么用

`from muse/` 下共 893 个文件，其中文献类 131 个（108 PDF + 23 XML），SHA256 去重后 122 篇，剔掉 21 个 shapefile 元数据（`.shp.xml`）→ **真文献 101 篇**。其余 762 个是提取出来的正文文本（147 份）、方法卡（6 份）、索引与清单等生成物。

### 成果

- `from muse/_text_all/`：101 篇里 90 篇成功提取正文（11 篇失败，多为扫描件或加密，逐条记在 `_提取记录.json`）
- `from muse/_方法卡/`：六份共 **99 张方法卡**，每张七栏，最关键一栏是「只用方法、不用他的数，我们该怎么做」

### 七类方法族（按能落到哪个模块分）

1. 把决策拆成串行门，而不是一个 logit
2. 从众：把「系数」换成「阈值分布」
3. 时间层：两个时钟，不能合成一个
4. 伤亡层：先分物理区，再选函数；分母先行
5. 水动力 → 行为：让水深改变参数，而不是乘一个折减系数
6. 验证口径：三层 + 分母 + 分集
7. ABM 结构：三段解耦、逐单元边际

### 最该记住的一条规矩

**文献的结论和量级可以当基本盘直接用**（例如「水越深越走不动」「洪水死亡以溺亡为主」「车在 0.5–0.6 m 开始漂」）；**不能做的是把别人某个样本的百分比，说成我们模型自己算出的结果**。

这条界线的具体案例见台账第六节「我们做错的三处」。

## 六、已改正的错误（含我自己判断失误）

这一节是给下一个 AI 的防坑指南——**下面每一条我都犯过，别重犯**。

### 6.1 跑了半新半旧的验证，还当结论用

11-19 上午启动的第一次验证（`web/out/step1/`）启动于 10:08，而 `incidents.js`(10:11)、`ped.js`(10:10)、雨强档(10:11) 都在它启动**之后**才改。结果死因全是旧键、分区为空——不是代码没生效，是跑的时候文件还是旧的。

**规矩：同一轮改了多个文件，中途启动的那次验证一律作废。跑之前用 `git status` 与文件修改时间核对。**

### 6.2 死因归类把「被困」整类吞掉（真 bug，已修）

`die()` 先把 `r.status` 改成 `'dead'`，`deathCode()` 之后才读 `status === 'stranded'`，这个条件永远为假。结果所有非车内死亡都被记成「涉水行走」，十例「深水被困」消失。

**规矩：新增统计口径必须拿旧口径交叉校验。** `deathsByLegacyCause` 就是为此保留的。改完要能逐项对齐，对不上就是坏了。

### 6.3 把「分布集中」当成「程序出错」（判断失误）

我曾断言「同伴留存比例只有两个极端值、中间八档全空，属于输入失真」。

**这是错的。** `peersStay` 是同伴中「没在逃」的比例，全城每天避险只有五十几个人（约 5%），任何人的同伴留存率在算术上就必然接近 1。加入更多工况后中间档是 12.5% → 33.2% → 47.2% → 52.7%，**随雨强单调上升**——雨大时避险的人多，比例才分散。这是正常结果。

而且 Borowski 的模型里同伴留存对「留下」的效应带威胁交互：威胁中档 −9.27、极高档 −21.13（p=0.000），威胁真上来时 +7.76 会被抵消成负数。机制本来就自洽。

### 6.4 外部验证两次都是阴性（重要，别掩盖）

**验证一：DC 311 报修不能当路面积水证据。** 下载 2023–2025 年 775 条积水报修，去重 706 个点，拿它们撞 DC 官方自己的内涝范围，只有 **2.1%** 落在里面。这批报修主要是下水道返水、进屋淹水，不是街道积水。**拿它验证街面积水会得出错误结论。**

**验证二：我们的积水图与 DC 官方模型几乎不重合。** 20 m 网格逐点比对，CSI 只有 **0.017**（精确率 2.9%、召回 4.3%）。

**但不能就此判「模型错了」**：口径完全不同——我们是 50 mm/h 稳态、**没有管网、没有河道、没有潮位**；官方是 1 年一遇、含河道与管网。能说的只有一句：**目前没有任何证据支持「我们的积水位置和现实一致」**，报告里只能写到「模型自洽」。

### 6.5 「已接入」说早了

11-18 我说「逐栋首层标高已接入」，实际只接了 **Python 判淹侧**（`simple_drainage.py`），**JS 运行时从来没读过** `building_foundation.json`。也就是说浏览器里的室内淹层判定，用的还是旧数据。

另外当天先用「截断到 1.2 m」处理雷达系统偏差，方向是错的：1.2 m 比真实台基高一倍，把淹楼数从 3,358 压到 540，**低估了 3–4 倍**。改用 FEMA 规范值做分位数映射后是 130–200 栋（三组基础类型假设都在这个区间，且与 DC 规范值 142 互印证）。

### 6.6 「全城」这个说法不成立

计算域只有约 **5.2 × 4.4 公里**的市中心。774 个 311 报修点里 535 个在域外。所有结论只对市中心成立。

### 6.7 把别人的观测值搬来改自己的模型

曾按桑迪调查的「网络平均 2.69 人、34.3% 同伴在 5 英里外」，去改我们生成人群的组网规则。**已撤销**（`git checkout` 回退），原因有二：一是拿别人观测值凑我们的模型，二是实测也证明无效（中间档只 7.6%，死亡仍 9）。

### 6.8 文献同源问题

`params.js` 里的涉水速度表（0 / 0.35 / 0.60 / 0.90 m）与文献4 的 D-1（Li, Chen, Song 2025）是**同一批中科大泳池实验的两次发表**（水深档一致、0.90 m 档 0.81 m/s 一致），不能当独立验证，只能算单一来源。

## 七、已知缺口（按「能不能解决」分四类）

### A. 已有依据、只差动手

| 缺口 | 现状 | 怎么补 |
| --- | --- | --- |
| 首层标高接进 JS 运行时 | Python 侧已用 FEMA 校正值，浏览器侧没接 | 读 `data/derived/building_foundation_fema.json`，改 `incidents.js` 的室内淹层判定。**会改伤亡数字，要重跑** |
| 避难所容量 | `ped.js` 的 `R.cap = 12/8` 是防扎堆的散布参数，**不是建筑容量** | 红十字标准已有：短期 1.9 m²/人、长期 3.7 m²/人。把网格点关联到建筑，按 footprint 面积除算容量 |
| 时间层拆两个钟 | 现在只有「预警什么时候到」一条线 | 台账方法族 3 有做法：①发布→收到（含 35% 收不到）②收到→出发（给分布不给常数） |

### B. 要补物理量，工程量中等

| 缺口 | 卡在哪 |
| --- | --- |
| 流速场 | 水模型只输出水深，不输出流速。没有流速就判不了「被冲走」，也判不了 Jonkman 的溃决区（现在 `velocityMs: 0`），**伤亡系统性偏低** |
| 非溺亡死因 | 死因已改成「地点×动作」两维，能和个案库对照了；但「被砸／触电／被冲走」仍判不了，缺的正是流速与结构破坏 |

### C. 缺数据，靠检索解决不了

| 缺口 | 为什么 |
| --- | --- |
| 真实人际网络 | 桑迪 ego network 数据不公开；Add Health 要申请且不对 DC。现在只能用合成网络（户规模按 ACS 真实分布，**配对是凑的**，代码与文档都标了） |
| 有序 logit 的截距 | 原文不印，只有作者有 |
| DC 真实洪水逐人轨迹 | 不存在公开数据 |
| 失稳 → 伤亡的定量函数 | 检索四轮，确认没有剂量—反应函数 |

### D. 结构性重构

| 缺口 | 现状 |
| --- | --- |
| 内核／显示真正分离 | 现在只是**文件级分离**（`kernel/` 不引用 three/window，有自动检查）。但仿真推进仍挂在页面 `main.js` 的帧循环里，**没有纯 Node 入口**，不开浏览器就算不了 |
| 空间分片、多核 | 现在并行只在**工况级**（`sim-sweep.mjs` 一工况一个浏览器），一次仿真内部仍单线程串行 |

## 九、怎么跑

```bash
# 自检（纯 Node，不启浏览器，约 1 分钟）
cd web && npm test

# 单个工况跑一天
cd web && node sim/sim-day.mjs u_p8_s0 1000 1440 out/xxx

cd web && node sim/sim-sweep.mjs u_p20_s0,u_p40_s0 2 1000 1440 out/sweep2
```

**并发不要超过 4**：一个无头 Chrome 跑这套模型占 1.2–1.6 GB，本机物理内存约 4 GB，开多了会换页反而更慢。

**单工况墙钟约 1.8 小时**（1000 人 × 1440 分钟）。

## 十、红线（违反会白跑）

1. **重跑期间不许改 `web/src/*.js`**——后面的工况会重新加载页面，改了就加载到不同版本，整批作废。
2. **内核层不许引用 `window` / `document` / `three`**——有自动检查，破了就失去「能脱离浏览器算」的基础。
3. **不许把文献里别人样本的百分比，说成我们模型算出来的结果。** 文献值可以当基本盘、当参考、当对照，但必须标明来源与性质。
4. **找不到依据的参数必须显式标「目前自己定的」**，不许默默当事实用。这类参数集中在 `web/src/kernel/thresholds.js` 与 `params.js`，台账里列了。
5. **改了计算逻辑就要重跑**，不能拿旧数字配新代码。
6. **新增统计口径必须与旧口径交叉校验**（§6.2 的教训）。
7. **改动前先说清改哪个文件、哪几行、数字预计往哪走**（用户明确要求）。
