## 一、先说一件最容易搞错的事：八个工况不是一个家族

工况定义在 `web/sim/sim-sweep.mjs` 的 `ALL_CASES` 里，分成两族，**雨型不同，不能横向比**：

| 家族 | 工况 | 雨怎么下 | 24 小时总雨量 |
| --- | --- | --- | --- |
| 全天连绵雨 | 8 / 16 / 24 / 32 mm/h | 0–1440 分均匀下 | 192 / 384 / 576 / 768 mm |
| 傍晚暴雨 | 20 / 40 / 80 / 120 mm/h | 只在 17:00–19:00（第 1020–1140 分）下两小时 | 40 / 80 / 160 / 240 mm |

所以「32 mm/h 死 43 人、120 mm/h 只死 23 人」不是模型坏了，是两天完全不同的事：前者全天泡在雨里，后者只有傍晚两小时猛下一阵。**跨族比较一律不成立，报告里必须分开写。**

### 20 mm/h 为什么没跑完（诊断）

**慢是结构决定的，不是卡住。** 一次 24 小时仿真要产生 2000–2500 万次决策判断，全部在页面里单线程同步跑：Node 每批调一次 `window.__frame(0.1, 100)`，一口气推 100 帧，共 360 批。以跑完的 p40 为参照，全程 5,820 秒，摊下来每批约 16 秒、每仿真小时约 4 分钟，跑一天墙钟 1.6 小时。想更快只有两条路：多工况并行（已有，4 并发 3.83×），或把仿真从页面拆成纯 Node 内核（缺口 D，未做）。

**三次中断不在同一个点：** 960 分（66.7%）、840 分（58.3%）、440 分（30.6%，2026-11-19 21:07 按用户要求停跑）。

**已经能排除的：**

- **不是某个人或某条路径转不出来。** 840 分那一格，p20 的累计判断数与 p40 完全相同（都是 2,486,967 条），p40 只用 172 秒就过去了。同一批人、同一时刻、同一段代码，计算量没有异常。
- **不是水情突变。** 840 分是 14:00，两族雨都在 17:00（第 1020 分）才开始，此刻全城干燥。
- **不是内存单调泄漏。** 整机 15.4 GB；单跑时那个无头 Chrome 常驻 2.0–2.5 GB，连续 6 分钟采样在 2195→1982→2211→2504→2364→2278 MB 之间上下浮动，随 GC 起伏。

**还没排除的：** 那一批 `p.evaluate` 为什么没有返回。脚本对这个调用**没有设超时**，所以页面一旦不返回，外部看到的就是日志静默（上一次静默 27 分钟后进程以退出码 4294967295 结束），没法判断是页面死循环、渲染进程被系统结束，还是别的原因。四并发时每个 Chrome 2–3 GB、合计 9–10 GB，提交内存被吃掉大半，这是目前最可能的触发条件，但崩的时候没有留 dump，**没有直接证据，不当作结论**。

**下次跑之前该做的两件事**（只加观测，不动计算）：① 给每批 `p.evaluate` 加超时，超时就打印「卡在第几分、第几批、当时在场人数」再退出，避免又一次 27 分钟静默；② 同一分钟的判断数要与已跑完的工况逐格对表，作为完整性校验（目前 p20 与 p40 在 840 分及之前完全一致）。

## 四、从这批结果里能看出来的四条

**一、族内随雨强单调上升，没有翻转。** 全天族 7 → 23 → 40 → 43；暴雨族 0 → 1 → 9 → 23（20 mm/h 已补）。这是最基本的可信性检查，通过了。

**二、「被困」和「涉水」的主次随雨强翻转。** 8 mm/h 时被困占 5/7；32 mm/h 时两者几乎持平（21 对 20）。雨小水深不够淹死人，但人走进深水区出不来，先被困住；雨大水里真能淹死人，涉水死亡追上来。

**三、地下室死亡开始出现，且随雨强增加。** 32 mm/h 出现 1 例；暴雨族 40 / 80 / 120 分别是 1 / 3 / 5 例。这是 11-19 新增的「地下室地坪埋深 + 进水判据」开始起作用。**注意：地下室地坪埋深 2.2 m、35% 的人会下去，这两个数目前是自己定的**（见 `docs/依据台账.md`），所以这一列不能当研究结论，只能当「模型里有这个机制」。

**四、「同伴留存中间档占比」只在同一族内随雨强上升。** 全天族 12.5% → 33.2% → 47.2% → 52.7%；暴雨族反而是 2.3% → 4.0% → 5.4%（更低）。原因不是矛盾：这个比例取决于「有多少人正在外面走动」，暴雨下在傍晚，多数人已在家，同伴几乎都没在逃，留存率全挤在 1 附近。**所以此前「二极化是 bug」的判断仍然是错的，但也不能说成「雨越大中间档越多」——要加「同一族、同一时段」这个前提。**

## 七、怎么复现

```bash
cd web
# 单工况
node sim/sim-day.mjs u_p8_s0 1000 1440 out/xxx
# 多工况并行（工况 / 并发 / 人数 / 分钟 / 输出目录）
node sim/sim-sweep.mjs all 4 1000 1440 out/sweep
```

单工况墙钟约 1.6–1.9 小时；并发别超过 4（一个无头 Chrome 实测常驻 2.0–2.5 GB，本机总内存 15.4 GB）。

**跑之前先 `git status` 确认 `web/src/` 没被改过**，否则不同工况是两套代码口径，不能进同一张表。

## 附录：数据来源

**一、本文所有伤亡、被困、避险、水深数字**

全部是**本项目的模型输出（仿真跑出来的，不是实测）**：

- 生成方式：`web/sim/sim-sweep.mjs` 启动无头 Chrome（Puppeteer `headless:'new'`）加载 `web/index.html`（本地静态服务 127.0.0.1:8140），由 `web/sim/sim-day.mjs` 驱动 1000 个个体连续跑 1440 分钟，帧倍率 24，共 36,000 帧。
- 固定种子：20261117（`web/sim/sim-sweep.mjs` 的 `SEED`，可用环境变量 `SIM_SEED` 覆盖）。所有工况用同一批人，只有水在变。
- 工况定义（雨强、雨型、降雨时段、增水）：`web/sim/sim-sweep.mjs` 的 `ALL_CASES`；每档的水深帧在 `web/assets/flood/<工况名>/manifest.json` 与同目录帧文件。
- 伤亡判定：`web/src/incidents.js`（`die()`、`deathCode()`），致死函数 `web/src/kernel/fatality.js`（Jonkman 三区）。
- 逐项复核入口：各工况 json 的 `final.sim.incidents`（`dead`、`everStranded`、`everInjured`、`evacuated`、`exposed`、`deathsByCause`、`deathsByZone`、`deathsByLegacyCause`）与 `final.sim.live.peerBins`；`hourly` 数组是逐时快照。
- 注意：`hourly` 最后一格是第 1440 分钟的**快照**，比跑完时的最终统计少 1 例（死亡／被困／避险各少 1），因为最后一次判定发生在快照之后。**以 `.md` 报告和 `final.sim.incidents` 为准，不要用 `hourly` 末格当总数。**

**二、用到的文献参数（不是本文的数据，是模型的输入）**

- 从众系数 7.76（标准差 10.87）、威胁交互项 −9.27 / −21.13、疏散 ASC 4.22：Borowski & Stathopoulos 2023, *Natural Hazards Review* 24(1):04022045, Table 4，DOI 10.1061/(ASCE)NH.1527-6996.0000577，n=586。
