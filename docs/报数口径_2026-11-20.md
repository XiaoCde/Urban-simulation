# 报数口径：死亡数当噪声，改报可积的量（2026-11-20）

## 一、问题：死亡列现在是伯努利噪声

p40（傍晚 40 mm/h）跑完全天，**累计判断 22,230,952 次，死亡 1 人**。
20 mm/h 那一档全天 0 人。20 → 40 → 80 → 120 mm/h 的死亡是 0 → 1 → 9 → 23。

0 和 1 之间、1 和 9 之间的差，都不是「模型算出了一个概率」，而是
**同一个概率在 1000 人身上抽了一次签**：1000 人、每人一条命，期望死亡数如果是 0.6，
那么跑出来 0 或 1 都是常态（泊松：P(0|0.6)=55%，P(1|0.6)=33%）。

所以：

- 「20 mm/h 不死人、40 mm/h 开始死人」这种句子**不能写**。它不是门槛，是抽样。
- 想说「这一档比那一档更危险」，必须报**连续量**（暴露、涉水、被困时长、概率积分），
  或者报**多次重复的均值**。现在的死亡列两样都不是。

## 二、能报的量（都有现成数据，不需要改内核）

| 量 | 定义 | 现在有没有 |
| --- | --- | --- |
| 涉水暴露人数 | 某一刻处在可涉水深度以上的人 | 有：`incidents.wading` / `hourly[].wading` |
| 被困人数 | 某一刻被判被困的人 | 有：`hourly[].stranded` |
| **被困人·时** | 逐小时被困人数 × 1 h 求和 | 可以算（24 个整点快照，矩形求和，偏粗） |
| 累计被困 | 当天至少被困过一次的人 | 有：`everStranded` |
| 受伤人数 / 受伤人·时 | 同上 | 有 `hourly[].injured` / `everInjured` |
| 避险人数 | 主动转移到高处/离开危险区的人 | 有：`evacuated` / `everEvacuated` |
| 期望死亡 | 逐人逐秒死亡概率积分之和 | **没有**（`INC` 里 `floodRisk` 是人级累加，未导出） |

**本轮的报数改动**（只改验收层 `web/sim/sim-day.mjs`，不动内核）：

1. 摘要表把「死 N 人」后面加一列 `被困人·时`（24 点矩形和）与 `涉水人·时`，标注算法。
2. 死亡列**永远与「期望死亡」并列**；暂时没有期望死亡时，明确写「死亡数为单次抽样，不具可比性」。
3. 工况对照改成报「暴露 → 涉水 → 被困时长 → 避险」这条链，死亡放最后并加 ⚠。

> 有意的取舍：不改内核去导出 `floodRisk` 总和，因为这需要动 `incidents.js` 的内部状态，
> 而本轮已经改了两处结构（相机、首层高）。等 v2 结果出来再决定要不要把期望死亡做成正式出口。

## 三、泊松噪声的量级（给报告写「不要比」时的依据）

以 p40 全天 1 人为例：如果真实期望是 0.6–1.5 人/天，那么同一工况重跑（换种子）会得到
0、1、2、3 都可能。**同一工况换种子重跑，死亡数若在 0–3 之间波动，那是模型没变，不是模型不稳。**

若要把「雨强 → 死亡」这条曲线做出来，最少要 3 组种子 × 每档，报均值与区间；
这需要 8 工况 × 3 种子 = 24 次全天仿真 ≈ 20 小时墙钟（2 并发）。**本轮不做**，写在待办里。

## 四、两族不能横比的再确认

- 全天族：8 / 16 / 24 / 32 mm/h，雨从 0 点下到 24 点，总量 192–768 mm。
- 傍晚族：20 / 40 / 80 / 120 mm/h，只在第 1020–1140 分（17:00–19:00）下，总量 40–240 mm。

「32 mm/h 死 43 人 vs 120 mm/h 死 23 人」不是模型倒了，是两天不同的事：
前者全天泡着，后者两小时猛灌。**任何跨族的「雨越大死越多」论述一律不成立。**

## 五、单次抽样的呈现规则（写进以后的报告）

1. 死亡、受伤这类 0–个位数的计数，必须写「单次抽样」+ 期望/区间（有就写，没有就写「未导出」）。
2. 报「差值」时不能只报差值：`|23−40|` 与 `|40−43|` 在 n=1000 的抽样下都可能反号。
3. 有连续量就用连续量说话；没有连续量时，只说「这一档的结构变化」——
   例如 8 mm/h 是被困主导（5/7），32 mm/h 是涉水与被困持平（21/20），
   这是**结构**差异，比绝对死亡数稳。
4. 每个表下面写清种子号与机位（v2 起机位已不影响结果，但仍要记，便于复现）。

## 六、查过代码之后：两条死亡路径的随机性根本不同（重要修正）

写这一节前专门去读了 `web/src/incidents.js` 与 `web/src/kernel/fatality.js`，结论比上面更具体：

| 路径 | 判死条件 | 随机性来源 |
| --- | --- | --- |
| 室内被淹（`incidents.js:386-406`） | 累计风险 `floodRisk ≥ personalThreshold(i)` | `personalThreshold(i)` 是**每人固定的 uniform(0,1) 抽样**（`fatality.js` 用哈希生成），`floodRisk` 由 `fatalRiskPerSecond(jk.fd)*h` 逐秒累加。所以**给定轨迹，死亡概率恰好 = `floodRisk`**（均匀分布 CDF 是恒等），期望死亡数 = `Σ min(floodRisk_i, 1)` |
| 室外涉水 / 被困（`incidents.js:508`） | `dExp ≥ instabilityDepth 且 deepSec > endurance` | `endurance = V.exposureSec × (0.72 + stamina×0.42) × …`（`:298-299`），**完全确定、没有抽样**。同一轨迹跑两次，死的人完全一样 |

这条差别决定了两件事：

1. **室内那条可以直接出「期望死亡」**，不需要多跑种子：把每人的 `floodRisk` 取 `min(·,1)` 求和即可。
   这个数比「本次抽样死了 N 人」稳得多，应该做成正式出口（`incidents` summary 里加一个字段）。
2. **室外那条不能**。它现在是确定性的，报告里「0 人死」和「20 人死」在换种子时的差别，
   来自轨迹分叉（相机、种群抽样、人群相互作用），不是概率抽签。
   要表示「离死多近」，只能导出**余量分布**：对每个暴露者算 `deepSec / endurance`，
   报最大值与 p95。这个量单次运行就有意义，且能证伪「阈值定得离谱」。

这两条都还没实现（本轮的 `docs/报数口径` 只到「指出问题」）；实现放在下一轮，
因为要改 `web/src/incidents.js`，而当前正在跑首层标高的 A/B。改法：

- `incidents.js` 的 summary 里加 `expectedIndoorDeaths`（Σ min(floodRisk,1)）与
  `outdoorMargin`（`{max, p95, n}`，对 `everInjured|everStranded` 或涉水过的人算）；
- 验收：同一份 v2 工况重放，`expectedIndoorDeaths` 必须与 `dead` 同量级
  （室内死者占 `dead` 的一部分，且 `expected ≥ dead` 恒成立——抽样死在期望上下浮动，
  但如果 `expected < dead` 说明风险累加被截断了，是 bug）。
