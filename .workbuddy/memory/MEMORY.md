# 项目约定（长期）

## 代码边界（用户明确要求，2026-11-13）
- 内核（判断、仿真计算）与显示层（three.js / DOM / 页面交互）必须分离。内核不得依赖 window / document / three 对象，要能纯 Node 命令行独立跑出与浏览器版一致的数字。
- 这是硬要求，不是后续优化项。之后每加新功能，先确定它属于内核层还是显示层；内核层不许反向引用显示层。
- 目的：后面要分块、上多核 / 分片 / 云机器，否则越往后越难改。
- 约定于 2026-11-14（明天）动手划边界，先出分块清单给用户确认再改代码。

## 数据与计划（用户明确要求，2026-11-14）
- 以后加任何功能、参数、分布、阈值，先找真实数据源或研究文献，写清出处；找不到就明确标注「目前自己定的」，不许把拍脑袋的数当结论交付。
- 每次动手前先列详细计划（步骤／每步改什么、产出什么／依据来源／怎么验／哪些待定），给用户确认后再改代码。
- 往回套的存量：9 年龄带、32 职业、圈层、一天 9 节点、门牌与人口分布、等红灯／礼让／接送孩子次数、伤亡阈值、决策公式系数，都要补一张依据台账（11/14 录音里被逐一点到）。
- **一切以真实数据为主，该替换就替换**（11/14 用户明确纠正）：现有决策模型、人群分类不必保留作对照，也不要为了保住已有结果搞新旧双实现并存。真实数据或文献说什么就改成什么，旧实现只归档、不留在运行时。验证口径是「与真实数据／文献对得上」，不是「与旧模型对得上」。
- 仍然留着的边界：确实找不到真实数据的项，必须显式标「目前自己定的」，不能因为「该替换就替换」就当成已经解决。
- **数据来源附录（2026-11-14 夜提出，23:42 与 23:51 两次纠正）**：所有数据都要有出处，**出处统一写在文档末尾的「附录：数据来源」里，正文不逐数字加编号、也不加自造代号**（用户明确说那样太乱、是黑话，要写正常中文或英文）。附录按来源逐条列：数据或文章全名、机构或作者、年份／版本、表号／页码／变量名、官方网页或 DOI、样本量、本地文件路径、拿到日期；分类用中文写明白「真实数据集／文献里的实测值／模型跑出来的数（不是实测）／目前自己定的」。**写的是数据真正的出处**（哪篇文章、哪个网站、哪个机构），不要写「Muse 给的」或「回件第几节」。
- **数据源本身也要写清（23:45 补充）**：不能只写「数据在哪个本地文件」，还要写这个**文件是哪来的**——发布机构、数据集全名、年份版本、官方下载页／目录页、官方引用格式、发布时间、谁在什么日期从哪个地址下载、校验值。否则别人会以为文件是凭空捏造的。样板：`from muse/数据来源.md`。
- **Muse 通道扩大（2026-11-14 夜）**：以后需要下载的数据、需要查找的资料，都可以列问题给用户转交 Muse（不限于本会话拿不到的情形）；回件统一放 `from muse/`，核验原件和数字后再接入。

## 外网数据与全组共性要求（2026-11-14 夜，详见《项目总览.md》§16）
- 外网原始数据拿不到时，把具体问题列给用户转交 Muse，带回原始表 / codebook / 确切数字；不许用摘要或估计值顶替。
- 四场录音（本人 + 另外两位同学 + 导师点评）里的共性要求：要回答「问题是什么／别人怎么做／我们为什么更好」，结果好不等于方法好；认知决策过程建模是跨同学的共性要求；日常行为代理灾害行为须有强文献依据；从众与二元触发式建模被点名；AgentSociety 类工作要讲清 framework 及我们方法与 LLM agent 的区别；ACS 要讲清字段、选型、分布一致性、空间粒度。
- 组里已有同学用 ACS、做人与人的影响、做分层并行，注意分工重合；NHTS 是日常数据，只能定日程基线，不能当灾害决策的证据。
- 需要外网查数时先写进《项目总览.md》§16.4 的问题清单，再交给用户。
